# Baram M1 — 부여성 첫 생활권

> AI 재개 지침: msw-planning의 resume 흐름으로 Baram-Roadmap.md, Archive/As-built.md, 이 문서와 남아 있는 Phase 문서를 먼저 읽는다. 구현·상태 변경 전에 references/build-management.md를 읽는다.
> 마지막 갱신: 2026-09-14 / 단계: Phase 1 데이터 기반 정리 진행 중

## 1. 한 줄 목표

선택한 외형의 캐릭터로 부여성에서 대화하고, 왕초보사냥터에서 토끼·다람쥐를 사냥해 얻은 물건을 푸줏간에서 팔고, 주막에서 물건을 구입·사용한 뒤 재접속해 상태를 이어간다.

## 2. 주요 결정

| 항목 | 결정 | 근거·범위 |
|---|---|---|
| 기반 | 기존 BaramMinimalTest 및 접속·외형·HUD·채팅 재사용 | 기존 플레이 가능한 베이스를 단계적으로 교체 |
| 맵 방식 | RectTile (1), 동적 플레이어는 KinematicbodyComponent 대응 | 기존 톱다운 방향 유지; 현재 수동 Transform 테스트 이동은 전환 필요 |
| 화면·입력 | 현재 PC 키보드/마우스 화면 기준 | 원본 조작은 baram.in/shortcuts와 비교 |
| 지역 | 부여성 14, 부여왕초보사냥1 315, 주막연실이네 15, 옥이네푸줏간 7 | 마을 1 + 사냥터 1 + 건물 내부 2 |
| 캐릭터 | 기존 성별·머리·국가·수호신 저장 유지 | 국가를 강제 변경하지 않는다. M1 생활권은 부여 지역부터 검증 |
| 플레이어 수 | 플레이어별 캐릭터와 서버 검증, 최소 2인 상호 확인 | 단일 로컬 BaramActor를 다인 플레이 완성으로 간주하지 않는다 |
| 콘텐츠 크기 | 주요 NPC 2명, 몬스터 2종, 기본 아이템 4종부터 | 원본 배치의 나머지 콘텐츠는 목록에 남기고 자동 활성화하지 않는다 |
| 난도 | 높음; 하나의 생활권을 먼저 완성 | 온라인 RPG의 데이터·동기화·상호작용 연쇄 검증 필요 |

## 3. 플레이 흐름

접속·외형 선택 → 부여성 진입 → 주막 대화 → 출입구 이동 → 토끼·다람쥐 사냥 → 도토리·토끼고기 줍기 → 옥이에게 판매 → 주모에게 동동주 구입 → 사용 및 수량·능력치 반영 → 종료·재접속 → 외형·위치·소지품·금전·성장 복원.

추가 실패 흐름: 거리 밖 NPC 사용 거절, 금전·수량 부족 거래 거절, 벽 통과 거절, 사망 후 안전 위치 복귀, 중복 보상 요청 거절.

## 4. 핵심 시스템과 근거

- 원본 데이터: Docs/BaramSource/m1-manifest.json. 각 행에 원본 파일·줄 번호를 보존한다. 정규화 결과는 분석용이며 런타임 적용 완료가 아니다.
- 맵: CMAP 헤더와 zlib 압축 해제, 셀당 6바이트를 확인했다. 충돌/오브젝트 의미와 픽셀 좌표 변환은 Phase 1에서 추가 확인한다.
- 몬스터: 다람쥐 id 1, HP 15, 경험치 10, 후제공격 타입 1. 토끼 id 2, HP 10, 경험치 5, 공격 불가 타입 2. 공격 수치의 최종 적용은 전투 함수 의미 확인 후 확정.
- 아이템: 목도 17, 동동주 2200, 도토리 3014, 토끼고기 3018. 지급·소비·가격은 관련 원본 스크립트와 DB로 검증한다. 목도를 생성 시 지급한다고 아직 가정하지 않는다.
- NPC: 연실네 id 8, map 15 (6,8). pursuit의 쥬모 → 주모를 해석하여 서비스에 연결. 옥이 id 11, map 7 (5,4), 구매 shop 20·판매 shop 21.
- 주막 서비스: M1은 대화·구매·판매만 활성화. 창고 등 경계는 Baram-Roadmap.md 참조.
- 전투·보상·거래·줍기는 서버가 거리·대상·수량·금전·중복을 검증한다. 대화·이미지는 클라이언트 UI로 표시한다.
- 성장: 원본 level_db와 기존 BaramLevelData의 일치 및 증가 공식을 먼저 확인한다. 초기 사냥에 필요한 성장만 연결한다.

## 5. 시스템과 MSW 구현 대응

| 시스템 | 구현 방향 |
|---|---|
| 세션·계정 로드 | 기존 BaramEntryFlow @Logic 확장, 버전 있는 저장 구조 |
| 플레이어 | 플레이어별 @Component + RectTile에 맞는 Body, 서버 상태와 클라이언트 표시 분리 |
| 맵·출입구 | MapBuilder/ModelBuilder, 원본 좌표 변환, 서버 이동 검증 |
| NPC·몬스터 | 역할별 .model + @Component; 맵 단위 스폰·정리 |
| 대화·가방·상점 | UIBuilder .ui + 클라이언트 UI 제어 |
| 기본 시스템 | msw-packages 카탈로그 먼저 평가, 원본 표현과 데이터 형식에 맞는지 확인 |
| 아이템·맵·배치·능력치 | 원본 ID를 유지한 정규화 데이터 → MSW UserDataSet/등록된 데이터 로직 |
| 외형·동작 | 기존 BaramAppearance 공유 목록 확장, 실제 NPC·몬스터 RUID 매핑 |
| 저장 | UserDataStorage, 이전 외형 레코드 호환, 테스트 키 분리 |

## 6. 단계별 완료 조건

### Phase 1 — 데이터와 첫 목표 고정
- ✅ 원본 DB·스크립트·맵 자산 목록과 M1 데이터 목록 생성, 핵심 행 검증.
- ✅ baram.in과 부여성 출입구·아이템 드롭·경험치 비교 근거 기록.
- ✅ 형식 예외 10개를 검토하고 첫 목표 선택 레코드에 영향 없음을 확인. 원문 예외 기록 보존.
- ⬜ CMAP 셀 의미·이동 가능 판정·타일과 오브젝트 리소스 매핑 확인.
- ⬜ 시작 장비·소비 효과·스폰 간격·드롭 함수 제어 흐름 확인 및 적용값 결정.

### Phase 2 — 캐릭터와 이동 기반
- ⬜ 로컬 테스트 액터를 플레이어별 캐릭터로 전환하고 선택 외형을 동기화.
- ⬜ 이동·방향·충돌·맵 좌표를 적용하고 채팅/대화 중 입력 충돌 방지.
- ⬜ 서버와 클라이언트 상태 소유 범위를 정하고 2인 이동·외형 확인.

### Phase 3 — 네 장소와 출입구
- ⬜ 원본 지형·오브젝트로 4개 맵을 구성하고 카메라·가림·충돌 확인.
- ⬜ 17개 포탈 행의 방향·도착점·레벨 조건 적용 및 왕복 테스트.
- ⬜ 음악·전환 표시 연결, M1 바깥 출입구는 이동 불가 상태를 명확히 표시.

### Phase 4 — NPC 상호작용
- ⬜ 연실네·옥이 외형과 배치 적용, 거리 확인·대화·선택·닫기 연결.
- ⬜ pursuit 해석과 원본 선택지에서 M1 서비스만 노출.
- ⬜ 대화 중 이동/채팅 입력과 NPC 중복 열기 검증.

### Phase 5 — 아이템과 거래
- ⬜ 기본 4종의 아이콘·수량·설명·장비/소비 데이터 적용.
- ⬜ 가방·줍기·구매·판매·사용·목도 장착 기능과 외형 연결.
- ⬜ 서버의 거리·재고·금전·수량 검사, 가방 부족과 중복 요청 검사.

### Phase 6 — 전투와 드롭
- ⬜ 토끼·다람쥐 원본 외형과 동작·배회·반격·사망·리스폰 구현.
- ⬜ 플레이어 기본 공격·피격·사망 복귀, 효과와 사운드 연결.
- ⬜ 서버 처치 판정과 경험치·드롭·줍기 소유권을 연결해 중복 획득 방지.

### Phase 7 — 초기 성장과 안내
- ⬜ 경험치·레벨·능력치와 HUD 연결, 초기 아이템 효과 확인.
- ⬜ 첫 생활권 안내를 연결하고 사냥→판매→구입→사용 흐름 확인.
- ⬜ 안내 목적의 새 진행 체크를 추가하면 원본 퀘스트와 구분하여 기록.

### Phase 8 — 저장과 통합 검증
- ⬜ 각 단계부터 연결한 저장을 통합 검증: 새 계정·이전 외형 저장·재접속·오류 복구.
- ⬜ 2인 상태·사냥·드롭·거래 격리 검증. 실제 2계정 결과 없으면 🟡 사용자 테스트 필요.
- ⬜ 모든 map/ 파일을 열거·검사하고 게임과 무관한 샘플 정리. 미사용 템플릿 맵은 보존/삭제 결정을 받은 뒤 처리.
- ⬜ 첫 생활권의 정상·실패 흐름을 Maker play/logs/input으로 검증하고 결과 기록.

### 사용자 우선 요청 — 상태창·그룹·교환 확장

세부 작업/검증 기록: `Baram-Profile-Social-Scope.md`. 기존 Phase 1~8의 검증 상태를 이 확장으로 완료 처리하지 않는다.

- 🟡 상태창 장비 7행·능력치 아이콘 전환·화살표 스크롤·원본 비트맵 글꼴.
- 🟡 교환·그룹 허가 ON/OFF와 원본 LOOKBTN 활성/비활성 이미지.
- 🟡 그룹 구성·가입·탈퇴·그룹장 권한·자동 승계·해체 및 G 이름 입력.
- ⬜ 원본 그룹 분배와 그룹 목록 화면.
- 🟡 원본 양방향 교환창·아이템/금전 제시·확인·취소·저장 복구 구현. 원본 창 3종 시각 검사, 분리 계산·저장 장애 8종·실제 CAS 검사 통과. 실제 두 사용자 간 검증 미완료.
- ⬜ 전체 회귀 및 실제 두 사용자 검증.

### 사용자 우선 요청 — 멀티플레이 보완

세부 상태: `Baram-Multiplayer-Verification.md`.

- 🟡 입장/타이틀/종료 활성 상태와 관전자 표시 수명 연결.
- 🟡 로드·저장 중 접속 변경 경합 방지.
- 🟡 공유 드롭 1회 획득과 가방 부족 보존 검사.
- 🟡 활성 사용자만 같은 맵 채팅 송수신.
- 🟡 Maker 빌드·분리 검사와 1인 재입장 통과. 실제 두 계정 이동·사냥·교환·재접속 검증 필요.

## 7. 데이터 관리

원본 파일은 읽기 전용으로 보존하고 해시·출처·원본 ID를 추적한다. 분석 결과와 적용 데이터는 분리한다. 런타임 데이터 등록은 Phase 2~6 각 구현에서 함께 수행하며 이름 문자열만으로 서로 연결하지 않는다.
